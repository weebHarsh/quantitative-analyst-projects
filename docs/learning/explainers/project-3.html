One board, two venues

Numbers: tests and benchmark run on 2026-11-15, synthetic feeds. Source: projects/03-market-data/README.md and bench/run_bench.sh

Two venues send updates in different formats. We need one board.

Each venue describes the same market in its own way. The program turns both into one set of events, then keeps one board per venue.

Each update edits the board, and zero quantity means remove.

A tested rule: the book never stores a row with zero quantity. A checker also flags a board where a buyer is at or above a seller (crossed or locked).

Prices are whole numbers of ticks, never decimals.

A missing message means the board may be wrong.

On a 15-minute test feed with injected faults, each venue showed 2 gaps and 3 resyncs. After each resync the rebuilt board matched the venue's own checkpoint (a full image the venue sends every so often).

Three kinds of bad message, three different responses.

Merge the boards, and leave out any stale venue.

A merged quote where buyer meets seller (locked) happens because Venue B lags Venue A: 1,017 times in one 15-minute test feed. The export filters them out.

Millions of updates a second, each applied in about 75 nanoseconds.

The timer's own cost (29 ns) is included in the update times, so they are upper bounds. Parsing, not the board, is the slowest step.

The clean quote file feeds Project 1 and, next, Project 4.

These feeds are synthetic and the two formats are modelled, not copied from a real venue. The method is real. No real venue was reachable.
